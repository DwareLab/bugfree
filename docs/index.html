Error tracking you own.

bugfree is a small, self-hosted Sentry alternative for Next.js and Express. It catches errors in the browser and on the server, un-minifies stack traces with your source maps, groups them into issues and tells you when something new breaks. It's free and open source.

Browser, Node.js server, edge runtime, React error boundaries, server actions and route handlers.

Readable stack traces

Source maps from webpack and Turbopack turn minified frames back into your code, with source context.

Events are grouped into issues. You'll see users affected, tags, hourly trends and regressions.

Slack, Discord, any webhook, or email when a new issue appears or a fixed one comes back.

Built for AI agents

An MCP endpoint lets Claude and other agents list issues, read stack traces and resolve bugs.

Introduction#

bugfree has three parts:

  • SDKs (@dwarelab/bugfree-* on npm) that run inside your apps and report errors.
  • The API, an Express + Postgres service that receives events, symbolicates and groups them, stores them and sends alerts.
  • The dashboard, a Next.js app where you browse issues, manage projects and invite your team.

You run the API and the dashboard yourself, either on a server with Docker Compose or on Cloudflare Workers. Your error data stays in your own Postgres database. There are no seats, quotas or paid tiers.

Free and open source. bugfree is MIT-licensed. Use it for side projects, at work, in commercial products, or as the starting point for your own fork.

How it works#

  1. An SDK catches an error and posts it to /api/ingest/<project>?key=<public key>, along with breadcrumbs (clicks, navigation, fetch calls, console), request data, user and tags.
  2. The API un-minifies the stack trace with the source maps uploaded for that release.
  3. The event is grouped into an issue by exception type and its top in-app frames. Alerts go out when the issue is new, or when it was resolved and has come back from a new release (a regression).
  4. You open the issue in the dashboard and see the stack trace with source context, breadcrumbs, the request, tags and every event, plus the container logs from around that moment.

Quick start (local)#

You can try bugfree on your own machine in a few minutes. You need Node.js 20+ and Docker. It uses ports 3100 (dashboard), 4100 (API) and 5442 (Postgres).

git clone https://github.com/DwareLab/bugfree.git
cd bugfree
npm install
npm run build:sdk     # build the SDK packages used by the examples
npm run db:up         # Postgres in Docker
npm run dev:api       # API on :4100 (runs migrations on start)
npm run dev:web       # dashboard on :3100

Open http://localhost:3100. On the first visit you'll be asked to create the admin account.

For demo data, run npm run dev:seed. It creates a dev account and demo projects, and writes the env files for the example apps. Then make them throw:

npm run demo:express  # http://localhost:5050: click the links to throw errors
npm run demo:next     # production build + source map upload, then http://localhost:3200

Docker Compose#

The repository's docker-compose.yml runs Postgres, the API, the dashboard and a backup job. Prebuilt images are published as ghcr.io/dwarelab/bugfree-api and ghcr.io/dwarelab/bugfree-web.

  1. Get the code and configure it 
    git clone https://github.com/DwareLab/bugfree.git && cd bugfree
cp .env.example .env

    Edit .env. At minimum, set a long random POSTGRES_PASSWORD and your two public URLs:

    .env
    POSTGRES_PASSWORD=change-me-to-a-long-random-string
API_URL=https://api.example.com
APP_URL=https://app.example.com
COOKIE_DOMAIN=.example.com
COOKIE_SECURE=true
  2. Start it 
    docker compose up -d --build

    The API applies database migrations when it starts. The dashboard listens on :3100 and the API on :4100.

  3. Put TLS in front

    Point app.example.com at port 3100 and api.example.com at port 4100 through any reverse proxy. With Caddy:

    Caddyfile
    app.example.com {
  reverse_proxy localhost:3100
}
api.example.com {
  reverse_proxy localhost:4100
}

    If there's more than one proxy hop in front of the API, set TRUST_PROXY to the number of hops so client IPs are correct.

  4. Create your account

    Open https://app.example.com and create the admin account. Then create a project.

Note: NEXT_PUBLIC_API_URL is baked into the dashboard at build time from API_URL. If you change API_URL, rebuild the dashboard with docker compose up -d --build web.

Cloudflare#

A single command deploys bugfree to Cloudflare Workers. You don't manage any servers, and TLS and scaling are handled for you.

PieceRuns on
APIA Worker (bugfree-api) running the same Express app with Node.js compatibility
DatabaseYour Postgres, reached through Hyperdrive, Cloudflare's connection pooler
DashboardA Worker (bugfree-web) built with the OpenNext adapter
Retention jobAn hourly Cron Trigger on the API Worker

Before you start

  • A Cloudflare account on the Workers Paid plan ($5/month). Password hashing and source-map processing need more CPU time per request than the free plan allows.
  • A Postgres 14+ database reachable from the internet, for example Neon, Supabase, AWS RDS, or your own server with TLS. It needs the pg_trgm extension, which most hosted providers include.
  • Optional: a domain on your Cloudflare account. Without one you get *.workers.dev URLs.
  • Node.js 20+ and a clone of the repository.

Deploy

  1. Install 
    git clone https://github.com/DwareLab/bugfree.git && cd bugfree
npm install
  2. Run the deploy script 
    DATABASE_URL='postgres://user:pass@host:5432/bugfree?sslmode=require' \
  npm run deploy:cloudflare -- --domain example.com

    The dashboard is served on app.example.com and the API on api.example.com. For other hostnames, pass --app-host and --api-host.

    DATABASE_URL='postgres://user:pass@host:5432/bugfree?sslmode=require' \
  npm run deploy:cloudflare

    Both Workers get URLs like https://bugfree-api.<your-subdomain>.workers.dev. You can switch to your own domain later by re-running with --domain. The workers.dev URLs stay active, so DSNs that use them keep working.

    The first time, a browser window opens so you can log in to Cloudflare. Then the script:

    1. creates a Hyperdrive config for your database with query caching turned off, so the dashboard always shows fresh data,
    2. deploys the API Worker with your URLs, cookie settings and the hourly cron,
    3. builds the dashboard against your API URL and deploys it,
    4. calls the API's /healthz, which applies the database migrations on first start.
  3. Open the dashboard

    The script prints your URLs at the end. Open the dashboard, create the admin account and create a project. A new custom domain can take a minute or two to get its certificate.

To upgrade, run the same command again. The script saves the last run's settings, including the Hyperdrive id and your domain, in .cloudflare.json (gitignored). After git pull && npm install, run npm run deploy:cloudflare with no arguments. New database migrations are applied automatically.

Create a Cloudflare API token from the Edit Cloudflare Workers template. Add Hyperdrive: Edit, and Zone → DNS: Edit if you use a custom domain. Copy the Hyperdrive id from .cloudflare.json into a CI variable, then:

.github/workflows/deploy-bugfree.yml

Try the Workers build locally

These run the API and dashboard in workerd, Cloudflare's runtime, against the local Docker Postgres:

npm run db:up
npm run dev:worker -w @bugfree/api       # API on http://localhost:8787
NEXT_PUBLIC_API_URL=http://localhost:8787 \
  npm run preview:worker -w @bugfree/web # dashboard; set the API's APP_URL to match its port

Differences from Docker

  • Rate limits are per Worker instance. Cloudflare runs many copies of the API, so INGEST_RATE_LIMIT and login throttling are approximate. If you need a hard global cap, add a WAF rate limiting rule.
  • Source map uploads are limited by Workers' 100 MB request body and 128 MB of memory. Keep individual maps well under 50 MB.
  • Backups come from your Postgres provider. The Compose backup container isn't part of this setup.
  • API logs: run npx wrangler tail bugfree-api, or open Workers & Pages → bugfree-api → Logs in the Cloudflare dashboard.

Removing it

npx wrangler delete bugfree-web
npx wrangler delete bugfree-api
npx wrangler hyperdrive delete <id from .cloudflare.json>

Your data stays in your Postgres database until you drop it.

Domains, cookies & TLS#

The dashboard and the API run on separate subdomains of one domain, for example app.example.com and api.example.com. The browser calls the API directly, with no proxy in between.

  • The API allows credentialed CORS only from the origins listed in APP_URL.
  • The session cookie is HttpOnly, SameSite=Lax and, in production, Secure. Set COOKIE_DOMAIN=.example.com to share it across your subdomains. The Cloudflare script sets it for you.
  • Every write is CSRF-checked against the Origin header.
  • Because both hosts are on the same site, the cookie keeps working in browsers that block third-party cookies.

Keep both on one domain. If the dashboard is on example.com and the API on other.net, browsers treat the session cookie as third-party and logins won't stick.

Upgrades & backups#

Upgrading

Database migrations run automatically when the API starts, so to upgrade you just run the new version.

git pull
# pin a release in .env (BUGFREE_VERSION=0.2.0) or keep "latest"
docker compose pull && docker compose up -d
git pull
npm install
npm run deploy:cloudflare

Backups (Docker Compose)

The backup service writes a compressed pg_dump to ./backups every BACKUP_INTERVAL_HOURS (default 24) and keeps BACKUP_KEEP_DAYS (default 7) days of them. Copy that folder somewhere off the server. To restore:

docker compose exec -T db pg_restore -U bugfree -d bugfree --clean < backups/bugfree-<date>.dump

Projects & DSNs#

A project is one app or service. Create one in the dashboard. Its Settings & setup page shows copy-paste snippets with your values filled in, plus two keys:

  • DSN: a URL containing the API address, the project id and the public key. It goes into your app and is safe to ship to browsers, because it can only submit events.
  • Secret key: used by the CLI to upload source maps. Keep it in CI secrets and never ship it to a browser.

Each project has its own alert settings. Use the Team & account page to invite members and create API tokens.

Next.js#

For the App Router on Next.js 15 and later. One package covers the browser, the Node.js server and the edge runtime.

npm install @dwarelab/bugfree-nextjs
npm install -D @dwarelab/bugfree-cli
  1. Set the environment variables
    .env
    NEXT_PUBLIC_BUGFREE_DSN=https://…@api.example.com/1   # from the project's setup page
# optional: set per deploy (git sha, version …); must match the source map upload
BUGFREE_RELEASE=my-app@1.0.0
  2. Initialize in the browser
    instrumentation-client.ts
    import { init } from "@dwarelab/bugfree-nextjs/client";
init(); // reads NEXT_PUBLIC_BUGFREE_DSN / NEXT_PUBLIC_BUGFREE_RELEASE
  3. Initialize on the server and edge
    instrumentation.ts
    export async function register() {
  if (process.env.NEXT_RUNTIME === "nodejs") {
    const { init } = await import("@dwarelab/bugfree-nextjs/server");
    init();
  }
  if (process.env.NEXT_RUNTIME === "edge") {
    const { initEdge } = await import("@dwarelab/bugfree-nextjs");
    initEdge();
  }
}
export { captureRequestError as onRequestError } from "@dwarelab/bugfree-nextjs";

    onRequestError reports errors from server components, route handlers and server actions.

  4. Report errors caught by error boundaries
    app/error.tsx and app/global-error.tsx
    "use client";
import { useReportError } from "@dwarelab/bugfree-nextjs/client";

export default function Error({ error, reset }: { error: Error & { digest?: string }; reset: () => void }) {
  useReportError(error);
  return <button onClick={reset}>Try again</button>;
}
  5. Enable source maps
    next.config.ts
    import { withBugfree } from "@dwarelab/bugfree-nextjs/config";
export default withBugfree({ /* your config */ });

    This turns on production browser and server source maps and bakes the release into the build.

  6. Upload source maps after each build 
    # BUGFREE_URL = your API URL, BUGFREE_AUTH_TOKEN = the project's secret key
next build && bugfree sourcemaps upload --nextjs --delete-after

    --delete-after removes the browser maps from .next/static so they aren't served publicly. Server maps stay. See Releases & source maps.

Good to know

  • Server render errors are tagged with the digest that error.tsx shows your users. If a user sends you "Reference: 2128315299", search for digest:2128315299.
  • Hydration mismatches are tagged react.hydration:yes.
  • On Vercel and other serverless hosts, events are handed to the request's waitUntil, so they're delivered even when the function freezes right after the response.

Express#

Works with Express 4 and 5. The package includes the Node.js SDK.

npm install @dwarelab/bugfree-express
server.js
import * as Bugfree from "@dwarelab/bugfree-express";
Bugfree.init({ dsn: process.env.BUGFREE_DSN, release: process.env.BUGFREE_RELEASE });

import express from "express";
const app = express();
app.use(Bugfree.requestHandler());     // per-request scope: breadcrumbs, user, request data

// … your routes …

Bugfree.setupExpressErrorHandler(app); // reports errors without a status or with status >= 500
app.use((err, req, res, next) => res.status(500).json({ eventId: res.locals.bugfreeEventId }));
  • Call init() before importing anything else so that every module is covered.
  • Express 4 ignores promises returned by handlers. The SDK forwards rejected async handlers to next(err), so those errors reach your error handler with the request attached instead of hanging the request. Turn this off with requestHandler({ patchAsyncHandlers: false }).
  • Outgoing requests made with fetch and with http/https (axios, got, node-fetch) are recorded as breadcrumbs.
  • On SIGTERM/SIGINT the SDK delivers queued events before the process exits, so errors from a rolling deploy aren't lost.

Node.js#

For plain Node.js services, queue workers, cron jobs and scripts:

npm install @dwarelab/bugfree-node
worker.js
import * as Bugfree from "@dwarelab/bugfree-node";
Bugfree.init({ dsn: process.env.BUGFREE_DSN, environment: "production" });

try {
  await processJob(job);
} catch (err) {
  Bugfree.captureException(err);
}
await Bugfree.flush(); // before a short-lived script exits

Uncaught exceptions and unhandled rejections are reported automatically.

Releases & source maps#

Production JavaScript is minified, so a raw stack trace points at something like main-3f2a.js:1:48213. Once you upload your source maps, bugfree shows the original file, line and surrounding code instead. Maps are stored per release, and each event is symbolicated with the maps of the release it reports.

How the release is detected

The SDK, withBugfree and the CLI all pick the release the same way, so events and maps always match:

  1. BUGFREE_RELEASE, if it's set,
  2. otherwise the commit SHA from your CI or host: Vercel, GitHub Actions, GitLab, Render, Railway, Heroku, Netlify or Cloudflare Pages,
  3. otherwise git rev-parse HEAD.

The CLI

npm install -D @dwarelab/bugfree-cli

# Next.js: uploads .next/static and .next/server maps
bugfree sourcemaps upload --nextjs --delete-after

# Any bundler: upload a directory; artifact names start with the URL prefix
bugfree sourcemaps upload dist --url-prefix ~/dist --release 1.4.0

# Create a release without uploading anything
bugfree releases new 1.4.0

A project's Releases page lists every release with its artifact count and size, new issues and events. You can delete a release's maps there. Maps of releases that have been idle for ARTIFACT_RETENTION_DAYS are cleaned up automatically, except for each project's newest few releases.

Issues & search#

The issue list shows each issue's title, where it happened, how often it occurs, the users affected and a 24-hour sparkline. Select several issues to resolve or ignore them in bulk.

Statuses

  • Unresolved: the default view.
  • Resolved: you shipped a fix. If the error comes back from a release that hadn't had it before, the issue reopens as a regression and alerts fire. Events from releases that already had it, such as browser tabs still running the old JavaScript, are counted but leave it resolved. Events without a release always reopen it.
  • Ignored: hidden from the default view.

Search syntax

Free text matches the title and the culprit. key:value filters on tags. Put values that contain spaces in quotes.

QueryFinds
TypeError checkoutIssues whose title or culprit contains both words
is:resolvedResolved issues (also unresolved, ignored, all)
browser:"Mobile Safari"Issues with that tag value (prefix match)
environment:productionIssues seen in production
digest:2128315299The Next.js server error behind a user's error reference
react.hydration:yesHydration mismatches

Any tag you set with setTag can be searched the same way.

How grouping works

The fingerprint is the exception type plus the top 5 in-app frames, with paths normalized and line numbers and build hashes removed. Events without a stack are grouped by their normalized message. To control grouping yourself, set a fingerprint:

Bugfree.withScope((scope) => {
  scope.setFingerprint(["payment-timeout"]);   // or ["{{ default }}", "eu"] to extend the default
  Bugfree.captureException(err);
});

Alerts#

Each project can notify you when a new issue appears and when a resolved issue regresses. You get at most one alert per issue every 30 minutes. Set alerts up in the project's settings, then use Send test alert to check them.

Webhook (Slack, Discord, anything)

Paste a Slack incoming webhook or Discord webhook URL. Other services receive the same JSON and can use the structured issue object:

POST body
{
  "text": "*[shop] New issue:* TypeError: …",      // Slack
  "content": "**[shop] New issue:** TypeError: …", // Discord
  "kind": "new",                                // or "regression"
  "issue": { "id": 42, "title": "…", "culprit": "…", "level": "error",
             "project": "shop", "release": "1.4.0", "url": "https://app.example.com/issues/42" }
}

Email

Set SMTP_URL (and optionally ALERT_FROM) on the API, then add comma-separated recipients in the project's alert settings.

Container logs#

docker logs only lasts as long as the container. When docker compose up recreates it, the history is gone. Run the bugfree agent once per Docker host and every container's stdout/stderr is kept in bugfree instead, under Logs in the project sidebar. The project's Settings & setup page has this snippet with your DSN filled in:

docker-compose.yml
services:
  bugfree-agent:
    image: ghcr.io/dwarelab/bugfree-docker-agent:latest
    restart: unless-stopped
    environment:
      BUGFREE_DSN: "https://<public key>@api.example.com/<project id>"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
      - bugfree-agent:/data
volumes:
  bugfree-agent:
  • It follows running containers, plus every container started later, through the Docker Engine API. It supports the json-file (Docker's default), local and journald log drivers.
  • Read positions are saved in /data once the API has stored the lines. Restarting the agent, a container or the Docker daemon doesn't lose or duplicate lines. If the API is unreachable, the agent pauses and retries, and Docker keeps the lines until it catches up.
  • Stack traces stay together: indented continuation lines and Caused by: are folded into the line before them.
  • BUGFREE_INCLUDE / BUGFREE_EXCLUDE take comma-separated globs on the container or Compose service name. The label bugfree.logs=false skips a container. BUGFREE_INITIAL_TAIL (default 200) is how much history already-running containers contribute on the first start.
  • On an issue page, Logs around this event shows the logs from 5 minutes before the event to 1 minute after. It's narrowed to the event's container when the SDK's server_name is a container id, which is Node's default hostname in Docker. Use the same project's DSN for the agent to get this.

The Docker socket is root-equivalent. To narrow what the agent can do, run a socket proxy that only allows CONTAINERS and EVENTS, and set DOCKER_HOST=tcp://socket-proxy:2375.

Sending logs from anything else

POST /api/logs/<project id>?key=<public key> (or the x-bugfree-key header) stores up to 5000 lines per request. Gzip is allowed.

{ "host": "web-1", "logs": [{ "timestamp": "2026-10-25T10:00:00Z", "message": "GET /cart 500", "stream": "stderr",
  "container": "shop-api-1", "service": "api", "image": "shop/api:1.4" }] }

level is optional. It's read from JSON log lines (pino, bunyan, winston …), logfmt level=, or the text (ERROR, [warn], TypeError: …). Other fields of JSON lines are kept as attributes and are searchable as field:value.

AI agents (MCP)#

The API serves a Model Context Protocol endpoint at <API_URL>/mcp (Streamable HTTP). It lets coding agents like Claude Code look up your errors, read symbolicated stack traces and logs, and mark issues resolved once a fix ships.

  1. Create a token

    Go to Team & account → API tokens. A token acts as the user who created it and can see every project. Choose read-only if the agent shouldn't change issue statuses.

  2. Add the server to your agent 
    claude mcp add --transport http bugfree https://api.example.com/mcp \
  --header "Authorization: Bearer bfu_…"

    Any MCP client that supports Streamable HTTP and custom headers works the same way.

  3. Ask

    For example: "Check bugfree for new errors in the shop project and fix the top one."

ToolWhat it does
list_projectsThe projects you can see
list_issuesA project's issues, using the dashboard's search syntax
get_issueIssue details, plus the latest event's stack trace, breadcrumbs and request
list_issue_eventsThe events of an issue
get_event / find_eventOne event, by id or by the SDK's event id
search_logsContainer logs, e.g. around an event's time

Retention & limits#

  • Every hour, events older than RETENTION_DAYS (default 30) and log lines older than LOG_RETENTION_DAYS (default 14) are deleted. Issue counters are kept, and hourly stats are kept for 90 days.
  • Ingest is rate-limited per project to INGEST_RATE_LIMIT events per second (default 50, bursts up to 10×). Over the limit, the API answers 429 with Retry-After, which the SDKs respect.
  • Events are processed inside the ingest request, in one Postgres transaction. That suits tens of events per second in total. For bursty apps, use the SDK's sampleRate.
  • An event can be up to 1 MB. A source map upload can be up to 100 MB with Docker. On Cloudflare, keep each map well under 50 MB.
  • Login attempts are rate-limited per IP address.

Troubleshooting#

No events show up

  • Set debug: true in init() and check the console for delivery errors.
  • Check that the DSN points at a URL your app can reach. For browser errors, that means a public HTTPS URL.
  • Make sure init() runs before the error happens. In Next.js, instrumentation.ts must be in the project root (or in src/).
  • A 401 means the project id or public key in the DSN is wrong. A 429 means you've hit the rate limit.

Stack traces are still minified

  • The event's release must equal the release the maps were uploaded for. Compare the release on the event page with the project's Releases page.
  • With a generic bundler, artifact names must match the script URLs. A script served from https://site.com/dist/app.js needs --url-prefix ~/dist.
  • Upload after every build. A rebuild changes the minified output even if the code is the same.

I can't stay logged in to the dashboard

  • The dashboard and API must share one registrable domain (see Domains).
  • APP_URL must match the dashboard's origin exactly, including https:// and without a trailing slash.
  • With COOKIE_SECURE=true, both sites must be served over HTTPS.

Alerts don't arrive

  • Use Send test alert in the project settings. It shows the webhook's HTTP status and the email result.
  • Alerts only fire for new issues and regressions, at most once per issue every 30 minutes.

The Cloudflare deploy fails

  • Hyperdrive can't connect: the database must accept connections from the internet over TLS. Check the URL with psql "$DATABASE_URL".
  • Custom domain errors: the domain must be a zone on the same Cloudflare account, and the hostnames mustn't already have DNS records.
  • The API returns 500: run npx wrangler tail bugfree-api and reload the page to see the error.

FAQ#

Is bugfree compatible with the Sentry SDKs?

No. bugfree has its own small SDKs with a similar API (captureException, setUser, withScope …), so switching usually means changing an import and the init call.

Which frameworks are supported?

Next.js (App Router, 15+), Express 4 and 5, and plain Node.js. Other browser apps can use @dwarelab/bugfree-browser.

Does it do performance tracing or session replay?

Not yet. bugfree focuses on errors, with container logs for context.

Can I use it for commercial projects?

Yes. It's MIT-licensed, so you can use it, change it, and host it for your clients.
